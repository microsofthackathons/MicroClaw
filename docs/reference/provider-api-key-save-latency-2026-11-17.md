# API Key 保存耗时与优化

## 生产日志样本

2026-11-17（UTC+8）MiniMax 保存操作的可观测后端区间为 12:06:10.512–12:06:18.826，共 **8.314 秒**。`config.apply` RPC 为 **7.520 秒**。前置 API Key 验证和最终界面提示没有完整打点，不包含在这个区间内。

| 日志区间 | 耗时 |
| --- | ---: |
| 更新准备、提交校验 | 0.536 秒 |
| 配置写入及触发热更新 | 1.031 秒 |
| Gateway 热更新 | 3.931 秒 |
| 热更新完成到 RPC 返回 | 2.055 秒 |
| 确认配置已应用 | 0.062 秒 |
| MXC 状态复核和恢复 | 0.699 秒 |

以上是日志事件间隔，不能将“写入及触发热更新”全部归为磁盘写入。证据是桌面诊断日志的 `provider-save provider=minimax` 事件，以及 Gateway 同一时间段的 `config.apply`、reload 事件。

## 实现

对于 OpenClaw 2026.10.10，在 Gateway 支持 `config.set` 且配置允许热更新时，千问、MiniMax 的纯连接参数保存、纯连接移除使用 `config.set`，随后检查目标配置哈希、运行时已应用版本和实际保存的连接字段或条目缺失。其余变更继续使用 `config.apply`。

保存时仅允许修改指定提供商的 `apiKey`、`baseUrl` 和 `api`，以及首次添加空模型目录和默认 `models.mode=merge`。移除时必须只删除目标提供商条目，保持其他提供商、默认模型、智能体和插件配置不变，并且剩余的默认/智能体模型配置不能继续引用该提供商。需要清理模型引用、编辑模型目录或插件、修改其他配置的操作，以及旧版本和需要重启的模式，不使用该路径。仍保留乐观并发校验、API Key 验证和外层 MXC 事务；响应丢失时不重放请求。

与当前 `config.apply` 相比，`config.set` 不执行同一组重启通知/回执后处理。Gateway 的配置验证和持久化仍通过官方写入路径进行，客户端必须确认运行时版本已生效后才能完成保存。日志的 `method=config.set` 可用于确认新路径已启用。

## 隔离实测

使用同一份 OpenClaw 2026.10.10 运行时、独立临时状态目录、随机本地 Gateway 令牌和模拟 MiniMax 端点。两轮分别以 `config.apply`、`config.set` 完成首次新增连接，再交替修改模拟密钥。每次都确认配置已落盘、运行时版本一致、默认模型未改变且 Gateway 没有重启。

| 场景 | 原路径 | 新路径 |
| --- | ---: | ---: |
| 全新连接首次保存，各 1 次 | 11.730 秒 | 3.565 秒 |
| 预热后重复保存，各 4 次，中位数 | 2.758 秒 | 0.761 秒 |
| 预热后重复保存，范围 | 2.025–3.250 秒 | 0.744–1.784 秒 |

重复保存样本排除了每轮前两次调用。原始记录位于 `build/reports/provider-save/first-connection.config.apply.json` 和 `build/reports/provider-save/first-connection.config.set.json`。单次首次保存对照和少量重复样本只用于确认优化方向，不是稳定延迟保证。

该实测覆盖后端配置写入及生效确认，不包括真实 MiniMax 网络、MXC 状态复核、界面绘制或生产环境中的其他插件。因此不能据此宣称生产端到端耗时已经从 8.314 秒降到表中的数值。

## 复测

`desktop/src/provider-connection-save.integration.test.ts` 默认为跳过，显式设置以下变量后运行该测试文件：

- `MICROCLAW_OPENCLAW_TEST_PACKAGE_DIR`：待验证的 OpenClaw 2026.10.10 包目录。
- `MICROCLAW_GATEWAY_E2E_PARENT`：已创建的临时测试父目录；测试目录必须位于其中。
- `MICROCLAW_PROVIDER_SAVE_REPORT`：可选输出路径前缀，会追加 `.config.apply.json` 和 `.config.set.json`。

测试不会读取用户的 API Key，会过滤子进程继承的密钥环境，并将状态、配置、工作区和设备身份隔离。生产环境复测应使用更新后的桌面版本，分别记录首次保存、重复保存以及网络验证耗时。

## 移除连接

同日 12:38 的移除样本仍使用原 `config.apply` 路径，RPC 耗时 **6.804 秒**。日志中的热更新区间为 12:38:17.515–12:38:21.219，耗时 **3.704 秒**；到 12:38:22.837 返回 RPC 又经过 **1.618 秒**。返回成功和 `status=hot-applied` 表明移除已生效；途中其他插件的来源告警不能据此认定为移除失败。

轻量移除还会检查目标提供商键确实不存在；保留空对象 `{}` 或仅移除 API Key 都不能通过成功校验。如果此次操作同时清理默认模型、fallback 或智能体模型引用，将继续走原有完整流程。

真实 Gateway 集成测试在保存对照之后交替执行 `config.apply`/`config.set` 移除，每次用同一轻量保存方式恢复模拟连接，验证删除已经生效、默认模型未改变且 Gateway 没有重启。移除指标记录在报告的 `removals` 数组中，各轮前两次删除作为预热。

| 隔离测试轮次（排除预热） | 原路径移除 | 轻量路径移除 |
| --- | ---: | ---: |
| 第一轮 | 4.782 秒 | 2.896 秒 |
| 第二轮 | 19.121 秒 | 8.414 秒 |

每轮每条路径各保留一个非预热删除样本，原始数据在 `build/reports/provider-save/remove-connection.config.apply.json` 和 `build/reports/provider-save/remove-connection.config.set.json`。两轮新路径均更快，但绝对耗时波动明显，不能保证固定时延，也不能将这些隔离样本直接当作前述生产操作的复测。轻量写入完成之后仍需等待热更新与版本确认；移除不会因为写入 RPC 较快返回就提前报告完成。

保存/移除逻辑、MXC 状态处理、模型目录及设置界面的 204 项相关测试，以及两个真实 Gateway 场景通过。涉及默认模型或智能体引用清理的移除仍保留原路径。
