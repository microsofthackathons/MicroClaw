## “桌面客户端安装”在做什么

`desktop-60` 对应 [WindowsSetup.install_desktop_client](../../deployer/windows_setup.py)，本次耗时 **25.810 秒，占总时间 41.36%**。它负责把新的桌面程序放到 `%USERPROFILE%\.microclaw`，并确认内置 OpenClaw 运行时可用。

本次实际路径如下：

1. 检查已安装桌面包与当前安装包的身份及关键文件。完全匹配时可以跳过 ZIP 解压；本次日志走的是“检测到已有桌面客户端，将覆盖更新”。
2. 查询桌面进程，确认旧客户端没有在升级过程中重新启动，避免覆盖正在使用的程序文件。
3. 找到安装器自带的 `microclaw-portable.zip`，本次没有网络下载桌面包。
4. `_extract_desktop_zip` 将 ZIP 解压到安装目录内的临时 `payload`，检查可执行文件，再逐项把现有同名文件或目录移入临时 `previous`，将新内容移入正式位置。发布中途失败时尝试恢复旧内容，成功后清理暂存目录及被替换的旧内容。安装器状态目录不会因整目录清空而丢失。
5. `_prepare_desktop_runtime` 启动 `MicroClawDesktop.exe --prepare-installer-runtime`，检查内置 OpenClaw 缓存，校验返回路径、入口、版本标记和包版本。这个准备模式不打开正常桌面窗口，也不等待 Gateway 服务就绪。

## “更新检查及备份准备”在做什么

这是分析时合并的两项：**6.736 + 15.335 = 22.071 秒，占总时间 35.36%**。安装页面对两项都显示“正在准备 MicroClaw 更新”，结构化日志通过 `stageId` 区分。它们不连续执行，中间还有 Node.js、npm 源和 OpenClaw 检查。

### 前置检查：prepareUpgrade-18，6.736 秒

对应 [WebInstallerBridge._prepare_upgrade](../../deployer/webview_bridge.py) 和 [WindowsSetup.prepare_openclaw_update](../../deployer/windows_setup.py)：

- 检查 Gateway 端口、锁文件、桌面进程及其归属，确认有没有正在运行的安装实例。
- 若发现应用仍在运行，先请求用户确认再停止进程；**本次没有人工确认等待或关闭运行中应用的记录**。
- 检查旧安装事务是否中断、是否需要恢复，检查待处理的核心包升级记录。
- 识别现有 OpenClaw 版本及安装位置，判断是否需要更新，并拒绝意外降级。

这项主要回答“能否安全开始更新、是否有旧事务要处理”。本次没有记录实际执行中断恢复，也没有在此运行全量 Doctor 或重新安装同版本 OpenClaw。

### 备份准备：prepareUpgrade-52，15.335 秒

对应 [WindowsSetup.prepare_openclaw_upgrade](../../deployer/windows_setup.py) 和 [OpenClawUpgradeTransaction._backup_managed_state](../../deployer/openclaw_upgrade.py)：

1. 再次确认 Gateway 已停止、旧事务已处理，现有 OpenClaw 已达到目标版本。
2. 判断旧卸载程序是否与当前安装包一致，以确定是否需要将它包含在备份中。
3. 创建并锁定升级事务，选择 `managed-state` 备份模式，记录版本、路径及事务阶段。
4. 将选定的配置、技能和卸载程序内容复制到备份暂存目录。
5. 对复制的文件执行持久化刷盘，生成文件清单、事务元数据，发布完整备份并进入 `installing` 阶段；使后续安装失败时有可恢复的文件。
6. 清除旧“安装已提交”标记，等待后续验证和提交步骤写入新状态。

本次 17:07:21 进入这一步，17:07:26 打印开始备份，17:07:37 完成。约 5 秒位于备份日志之前，约 11 秒覆盖备份及收尾；这是秒级粗分，**15.335 秒不能全部标成文件复制时间**，也不能精确拆出复制与刷盘各占多少。

## 后续观测与优化重点

- 桌面安装与两次更新准备共 **47.881 秒，占 76.72%**，是本次老用户覆盖安装的主要成本。
- 先为桌面 ZIP 解压、文件替换、旧内容清理补独立计时，拆清目前的 20.498 秒差额。
- 将运行实例检查、事务检查、备份复制、刷盘和清单发布分别计时，避免将全部 22.071 秒归因于备份。
- 核查持久化卸载器是否需要携带完整桌面安装 ZIP，以及升级时能否减少这部分大文件复制。当前清单证明其体积很大，但现有日志没有证明移除它能节省多少秒；需要保持卸载、重试和恢复流程的完整性后再验证。
- 对 helper 的进程创建继续测量。本次 Popen 阶段为 4.476 秒，尚无足够证据直接归因到系统扫描、进程加载或调度。

## 实测之后的卸载器白名单修复

上述 62.410 秒和 682.59 MiB 是修复前的历史样本，保留原始口径。后续源码将卸载器发布、内容比较、管理状态备份和管理状态恢复统一到 [uninstaller_bundle.py](../../deployer/uninstaller_bundle.py) 的运行文件白名单。

事务顶层仍将 `_internal` 作为一个恢复单元，内部不再无条件递归复制，允许的内容为：

- `_internal` 根目录的 `.dll`、`.pyd`、Python 必需的 `base_library.zip`，以及冻结程序导入版本模块时必需的 `install-manifest.json`。
- Python/.NET/WebView 依赖目录：`_tcl_data`、`_tk_data`、`tcl8`、`clr_loader`、`pythonnet`、`webview`、`setuptools`、`yaml`。
- `deployer/assets` 下的 `uninstall_template.html`、`microclaw.ico`、`microclaw-uninstall.ico`。

桌面安装 ZIP、安装脚本、安装用技能资源、安装页面及其他未列出的内容不进入持久化卸载器，也不进入新的管理状态备份。`base_library.zip` 属于 Python 运行依赖，必须保留，不能用排除所有 ZIP 的方式处理。

已有卸载器即使运行文件与当前包相同，只要仍含旧安装资源，也会退出复用快路径，经过暂存、启动检查及发布流程替换为精简目录。发布失败仍恢复原来的卸载器；历史备份本身不被改写，恢复旧管理状态备份时也应用同一运行文件白名单。

本次回归覆盖运行依赖保留、安装资源排除、旧目录迁移、发布失败恢复、备份清单及旧备份恢复。后续增加 PyInstaller 运行依赖时，需要同步核对该白名单和打包运行验证，不能直接重新放开整个 `_internal`。

用本次真实安装器目录在独立测试目录发布精简卸载器，`--check-uninstaller` 退出码为 0，版本清单、Python 标准库和卸载页面资源与源文件一致。源包 EXE + `_internal` 为 682,185,267 字节，白名单保留 38,331,550 字节（36.56 MiB），减少 **94.38%**；源安装器中的桌面 ZIP 保持存在。

将同一规则应用到上述历史备份的文件清单，选中的文件由 1,107 个降至 1,036 个，字节数由 715,748,339 降至 71,937,440（68.60 MiB）。这是按清单计算的体积，历史备份没有被修改，尚未用重新打包的安装器测量新的完整安装耗时。
